Website, web app, PWA or native app?

A plain-English guide to the four options, what each one is good at, and where the limits are. It’s worth reading before you commission any kind of app.

1. A normal website

A website is mainly there to be read. It tells people who you are, what you offer and how to get in touch. It might have a contact form or a blog, but visitors don’t usually log in and work inside it.

If that’s what you need, my sister studio M Bailey Website Design is the right place to start.

2. A browser-based web application

A web app is software that runs in a web browser. People open it with a web address, usually sign in, and use it to do something: book a slot, update a record, track a job, pay a subscription or run a report.

The code runs on a server and in the browser, so one app can serve:

  • Android phones and tablets
  • iPhone and iPad
  • Windows computers
  • Mac computers

I design the layout to adapt to each screen size, so it works properly on a phone in one hand and on a large desktop monitor. You don’t need separate Android, iOS, Windows and Mac versions for ordinary browser-based features, and nobody has to download anything from an app store.

When I release an update, it goes live on the server and everyone gets it the next time they open the app.

3. A Progressive Web App (PWA)

A PWA is a web app with some extra parts that let supported browsers treat it more like an installed app. Depending on the device and browser, that can mean:

  • An icon on the home screen or desktop, opening in its own window without the browser’s address bar.
  • Some screens or data that stay available with a poor or missing connection, if that’s designed and built in.
  • Notifications, if the app is built for them and the user gives permission.

Things to know:

  • Installing works differently on each platform. Chrome and Edge on Android and desktop can show an install option. On iPhone and iPad, people add the app from Safari’s Share menu instead.
  • Offline use isn’t automatic. Each part of the app that should work offline has to be planned, built and tested. For many apps, especially ones that share live data between users, a connection is still needed for most tasks.
  • Notifications vary. On iPhone and iPad, web notifications are only available once the app has been added to the Home Screen, and support depends on the iOS version.

Not every project needs to be a PWA. I’ll recommend it when installation or offline access gives your users a real benefit.

4. A native mobile app

A native app is built specifically for one platform, such as iOS or Android, and is usually installed from the App Store or Google Play. Covering several platforms means separate builds, or a cross-platform framework that still produces separate apps, plus each store’s review process for every release.

Native is often the better choice when an app needs:

  • Deep or continuous access to hardware, such as Bluetooth devices, NFC, health sensors or background location tracking.
  • Demanding graphics or performance, such as 3D games or heavy video processing.
  • Reliable background tasks or notifications on every device, whether or not the app has been installed from the home screen.
  • An App Store or Google Play listing as part of how people find you.

Browser support for hardware features differs between platforms. The camera, microphone and location are widely available with permission, but features like Web Bluetooth and Web NFC aren’t supported in Safari on iPhone and iPad. If your app depends on them, I’ll tell you before we go any further.

The short version

If people need to log in and get something done on whatever device they have, a web app is usually the most direct route.

If it helps to have it on the home screen or partly available offline, make it a PWA.

If it depends on specialist hardware or an app-store listing, consider native.
